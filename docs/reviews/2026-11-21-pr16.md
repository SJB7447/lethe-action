## 발견 사항

### B16-1 — [P2] 핵심 균열을 놓쳐 보스가 회복해도 퍼펙트 연쇄가 종료되지 않는다

- 위치: `src/game/sim.ts:1349–1361`
- 관련: `step()`의 `updateBoss()` → `updateLock()` 순서, `onFragmentMissed()` (`:711–717`)

다운 시간과 핵심 조각 수명이 끝나는 스텝에서 `updateBoss()`가 먼저 `bossRecoverFromDown()`을 호출한다. 이 함수는 핵심의 `fragment`를 바로 0으로 만들고 숨기므로, 뒤의 `updateLock()`은 조각 만료를 발견하지 못한다. `fragment:close(missed=true)`와 `onFragmentMissed()`의 연쇄 종료 처리를 모두 건너뛴다.

실제 Sim과 기본 튜닝으로 재현했다.

1. 약점 세 곳에 조각을 열고 각각 새로운 공격 입력을 넣어 퍼펙트 타격했다. 보스 HP 19, 콤보 3, 퍼펙트 활성 상태로 다운에 들어갔다.
2. 핵심은 공격하지 않고 `frame(1/120)`을 진행해 보스가 일어날 때까지 기다렸다.
3. 회복 직후 핵심은 사라졌지만 **`combo=3`, `perfectMode=true`, `comboTimer=1.591667`**였다. 해당 대기 구간의 종료 관련 이벤트는 `boss:recover`뿐이고 `fragment:close`, `combo:end`, `perfect:end`는 없었다.
4. 이어서 화면 안의 되살아난 약점 반대 방향을 바라보며 록온하면, 남아 있는 퍼펙트 모드로 그 약점의 록온 진행도가 **0.024023** 증가했다.

일반 보스 약점 조각을 만료시키면 같은 코드의 `onFragmentMissed()`가 `perfect:end` → `combo:end` → `combo:change`를 발행한다. 핵심만 회복 경로가 이를 우회한다. 퍼펙트가 영구히 남는 문제는 아니며, 새 조각을 열지 않으면 남은 콤보 제한 시간 뒤에 끝난다. 하지만 놓친 핵심을 이용해 다음 약점 주기까지 퍼펙트 록온을 이어 갈 수 있다.

권장: 회복 시 아직 열려 있던 핵심은 조각 만료와 연쇄 종료 경로로 정리한다. 이미 타격해 소비한 핵심과, 시간 초과로 놓친 핵심을 구분해야 한다.

### B16-2 — [P2] 핵심의 `fragment:open.window`가 실제 다운 시간과 다르다

- 위치: `src/game/sim.ts:1342–1343`
- 관련: `openFragment()` (`:701–710`), `docs/EVENTS.md`의 `fragment:open` 및 `boss:down`

`bossDown()`은 일반 `openFragment()`를 호출해 이벤트까지 발행한 뒤 핵심의 `fragment/fragmentMax`만 `bossDownTime`으로 덮어쓴다. 따라서 같은 핵심에 대해 이벤트 소비자와 실제 게임 상태가 서로 다른 수명을 받는다.

기본값 재현에서는 **`fragment:open { window:0.63 }`**, **`boss:down { duration:3 }`**, 실제 핵심 **`fragmentMax=3`**였다. 프레임을 진행한 뒤에도 핵심 수명은 3초 기준으로 줄어든다. 자동 보조 배수를 바꾸면 일반 조각 시간만 달라지고 실제 핵심 시간과의 불일치는 남는다.

현재 fragments 그림은 상태의 `fragmentMax`를 직접 읽으므로 화면 조각이 0.63초 만에 사라진다는 뜻은 아니다. 문제는 이벤트만으로 타이밍을 받는 UI·효과음이 정확한 핵심 개방 시간을 알 수 없다는 것이다.

권장: 핵심의 실제 수명을 먼저 확정한 뒤 동일한 값으로 개방 이벤트를 발행한다. 일반 조각과 보스 핵심이 서로 다른 시간을 쓰더라도 이벤트와 상태 값은 일치해야 한다.

### B16-3 — [P2] 빠르고 얇은 파동이 약점 조각·록온을 소거하지 않고 지나간다

- 위치: `src/game/sim.ts:1280–1292`
- 지원되는 설정 범위: `src/debug/tuningPanel.ts:142–144`

파동은 반지름을 한 스텝만큼 증가시킨 **최종 위치**에서만 균열 중심을 검사한다. 이전 반지름과 새 반지름 사이의 이동 구간은 검사하지 않는다. 이동량이 두께보다 커지면 원래 지나가야 할 균열을 건너뛴다.

패널에서 허용하는 `bossWaveSpeed=1500`, `bossPhase2WaveBoost=2.5`, `bossWaveWidth=10`, 페이즈 2로 재현했다. 고정 스텝 1/120초에서 반지름은 한 번에 **31.25px** 증가한다. 보스 머리 균열은 파동 중심에서 **78px**인데, 검사 반지름이 62.5→93.75로 이동할 때 양쪽 모두 5px 반두께 밖에 있다.

실제 `frame(1/120)` 4회 뒤 반지름 **125px**, 머리의 열린 조각 **0.966667초**, 록온 진행도 **0.5**, `fragment:close` **0회**였다. 이동·판정 코드를 재구현한 계산만의 결과가 아니라 해당 Sim 프레임으로 확인했다.

**기본 44px 두께에서의 정적인 판정/그림 불일치는 아니다.** 기본 설정에서는 실제 소거가 발생했다. 지원하는 튜닝 조합에서 파동의 이동 궤적이 누락되는 문제다.

권장: 이전/현재 반지름 사이에 두께를 포함한 통과 구간을 검사하거나 필요한 서브스텝을 적용한다. 판정 누락을 숨기려고 실제 파동 두께만 키우면 그림과의 일치가 다시 깨진다.

### B16-4 — [P3] 보스 예고·다운 그림이 히트스톱 중에도 실제 시간으로 움직인다

- 위치: `src/scenes/placeholderArt.ts:273`, `:285`
- 기준: `docs/ART_GUIDE.md` 3장, `ArtView.time/realTime` 주석

새 보스 그림의 예고 깜빡임과 다운 맥동이 `v.realTime`을 사용한다. 게임의 보스 타이머와 파동 반지름은 히트스톱에 멈추지만 해당 표시의 위상은 계속 진행된다. 지침의 실제 시간 예외는 `hitFx.ts`의 타격 화면 효과이며, 적 몸체/공격 예고의 애니메이션 전체가 예외인 것은 아니다.

같은 보스 상태·게임 시간·타이머를 고정하고 `realTime`만 0→0.08초로 바꿔 실제 `placeholderArt.enemies()`를 호출하면, 예고와 다운 상태 모두 그리기 명령이 달라졌다. 파동 예고의 alpha는 1→0.4로 바뀐다.

권장: 보스 몸체·예고·다운 맥동은 게임 시간으로 그린다. 히트스톱 중 지속할 특별한 화면 강조가 필요하면 기존 화면 효과 예외와 구분해 정의한다.

### B16-5 — [P3] 새 보스 전투 판정 수치 일부가 tuning 밖에 고정돼 있다

- 위치: `src/game/sim.ts:1079`, `:1267`, `:1314`
- 기준: `AGENTS.md` 5번, `docs/ROLES.md` Codex 항목

주요 보스 값은 tuning으로 분리했지만, 보스 다이빙 유효 거리 **900px**, 파동 회피 성공 여유 **60px**, 핵심 퍼펙트 피해 배율 **1.5**는 새 로직에 직접 들어 있다. 이 값들은 도형의 선 굵기나 내부 상태용 표식이 아니라 실제 명중·보너스·피해를 결정한다.

예를 들어 기본 핵심 피해를 조정해도 퍼펙트 배율은 항상 1.5이고, 파동 두께를 패널에서 바꿔도 별도의 회피 여유는 고정된다. 보스 손맛을 설정·프리셋으로 재현한다는 저장소 규칙을 충족하려면 이런 값도 tuning에 있어야 한다.

권장: 핵심 퍼펙트 배율, 보스 다이빙 거리, 파동 회피 여유를 이름 있는 tuning 값으로 옮기고 필요한 패널 항목을 연결한다. 기존 공통 피격 코드에서 옮겨 온 수치나 고정 히트박스 상수까지 신규 결함으로 집계하지는 않았다.
