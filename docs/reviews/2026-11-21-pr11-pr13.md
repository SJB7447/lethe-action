## PR #13 — 발견 사항

### S13-1 — [P2] 다이빙 중 재시작하거나 끝 지점에 닿으면 종료 이벤트·오버레이가 남는다

- 위치: `src/game/sim.ts:265–275`, `:327–329`, `:1064–1068`
- 소비자: `src/ui/index.ts`의 `dive:start`, `dive:end`, `room:reset` 구독

스테이지의 R 키는 `reset()` 대신 `respawn()`으로 간다. 여기서는 `diveTimer=0`으로 취소하지만 `dive:end`나 `room:reset`을 발행하지 않는다. 기존 HUD는 `dive:start`에서 표시한 오버레이를 이 두 이벤트에서만 숨긴다.

재현: 게이지 100에서 다이빙 입력을 소비한 다음 프레임에 재시작 입력을 소비하고, 이후 200프레임을 진행했다. `dive:start` 뒤 `player:respawn`은 발생했지만 `dive:end`는 없었다. 실제 `initUI()` 구독 코드를 모의 DOM에 연결한 검사에서도 `#hud-dive`의 `show` 클래스가 남았다. 실험실 R 키는 계속 `room:reset`을 보내므로 이 새 스테이지 경로와 결과가 다르다.

끝 지점에서도 같은 수명 문제가 있다. R5 끝 지점 안에서 다이빙을 시작하면 `cleared=true` 뒤 `advance()`가 `updateDive()` 전에 반환한다. 5초를 진행해도 `diveTimer=1.341667`, `timeScale=0.15`, `dive:end` 0회로 남았다. HUD와 화면용 다이빙 상태가 정산 화면 위에 계속 유지된다.

권장: 재시작·클리어에서 활성 다이빙을 명시적으로 종료하고 상태와 이벤트를 함께 정리한다. 이벤트만 추가해서 `diveTimer`를 남기거나, 타이머만 지워서 구독자를 남기지 않도록 종료 경로를 통일한다.

### S13-2 — [P2] 한 렌더 프레임에서 `stage:clear`가 여러 번 발행된다

- 위치: `src/game/sim.ts:358–365`, `:1064–1068`

끝 지점에 닿으면 `step()`만 반환한다. 바깥 고정 스텝 루프는 `hitstop`만 검사하므로 같은 프레임의 나머지 스텝도 계속 돈다. `cleared` 검사는 다음 `advance()`에 진입할 때만 적용되어, 남은 스텝마다 끝 지점 판정과 이벤트가 반복된다.

재현: R5에서 플레이어 중심을 `(1050,820)`에 두고 `frame(1/60)`을 한 번 실행했다. `stage:clear`가 **2회**, 서로 다른 `time=0.008333`, `0.016667`로 발행됐다. 이 중복은 클리어한 프레임 안에서 발생한다. 이후 모든 프레임에서 계속 반복되는 문제는 아니다.

영향: 정산 화면뿐 아니라 이후 연결할 저장·보상 처리도 중복 실행될 수 있고, 최초 클리어 순간 뒤에도 기록 시간이 증가한다.

권장: 클리어 상태로 전환되면 현재 고정 스텝 루프도 중단하고, 클리어 이벤트는 상태 전환 시 한 번만 발행한다.

### S13-3 — [P2] 다이빙으로 증가한 콤보가 `maxCombo`에 기록되지 않는다

- 위치: `src/game/sim.ts:803–805`
- 관련: `src/game/sim.ts:1038–1043`, `:1067`

새 정산 기록 `stats.maxCombo`는 `strikeHit()`에서만 갱신한다. 기존 `updateDive()`도 `combo += count`와 `combo:change`를 발생시키지만 이 기록에는 반영하지 않는다. 그 뒤 추가 파고들기를 하지 않으면 실제 HUD에 표시된 최대 연쇄보다 정산 값이 작다.

재현: R4에서 플레이어 중심 `(1000,820)`, 게이지 100으로 다이빙하고 실제 프레임을 진행했다. `dive:impact.count=4`, `combo=4`였지만 **`stats.maxCombo=0`**이었다. `stage:clear`는 이 기록을 그대로 복사하므로 해당 최대 연쇄가 누락된다.

권장: 콤보를 증가시키는 모든 경로에서 최대값을 갱신한다. 다이빙을 최대 연쇄 집계에서 제외할 의도라면 HUD·정산의 의미와 문서에 그 예외를 명시해야 한다.

### S13-4 — [P3] 체크포인트의 체력 이벤트 순서가 문서와 반대다

- 위치: `src/game/sim.ts:1082–1084`
- 계약: `docs/EVENTS.md:36`

문서는 `checkpoint` 뒤에 `player:hp`가 이어진다고 명시하지만 구현은 `player:hp` → `checkpoint`다. R4 체크포인트에 HP 2로 접촉시키면 HP 5 이벤트 뒤 `checkpoint { id: 'cp-r4', roomId: 'r4' }`가 발생한다.

현재 단순 체력 표시 자체는 갱신된다. 다만 체크포인트 알림을 기준으로 다음 체력 이벤트를 처리하는 구독자는 계약대로 동작할 수 없다. 코드와 문서의 순서를 맞춰야 한다.

### S13-5 — [P3] 실험실 시작 좌표를 발 기준으로 재해석해 위치가 바뀐다

- 위치: `src/game/room.ts:57`, `src/game/sim.ts:254–255`

기존 `ROOM.playerSpawn=(160,700)`은 플레이어의 왼쪽 위 좌표였다. 이를 같은 숫자의 `LAB_ROOM.entries.start`로 옮겼지만, 새 로더는 입구를 발 중앙으로 해석해 반 너비와 전체 높이를 뺀다.

실제 생성 직후 좌표는 PR #11의 **`(160,700)` → PR #13 실험실의 `(149,660)`**이다. `?mode=lab`의 최초 진입과 R 초기화에서 모두 시작 높이·수평 위치가 달라져 첫 낙하와 카메라 기준도 바뀐다. 기존 실험실 동작을 보존하려면 입구 데이터를 새 좌표 의미에 맞게 변환해야 한다.

### S13-6 — [P3] 스테이지 전용 `room:enter`가 실험실 초기화에도 발생한다

- 위치: `src/game/sim.ts:261`
- 관련: `src/scenes/LabScene.ts:79–83`, `docs/EVENTS.md:35`

공통 `loadRoom()`이 모드 구분 없이 `room:enter`를 발행한다. 문서는 이를 “스테이지에서 방에 들어감”으로 정의한다. 실험실에서도 생성·R 초기화 때 `{ roomId: 'lab', name: '조작감 실험실' }`가 발생한다.

실제 씬의 `create()`와 실험실 `restart()`를 모의 표시 객체에 연결하면 `roomLabel='조작감 실험실'`, `roomLabelTimer=2`가 된다. 최초 실험실 이름 표시에는 모드 검사가 있지만 이벤트 구독에는 없어서, 실험실 R 초기화 후에는 전에는 없던 방 이름 표시와 카메라 즉시 이동이 적용된다.

권장: 문서대로 스테이지에서만 이벤트를 보내거나, 적용 범위를 넓힐 경우 실험실 표시·카메라 동작을 별도로 보존하고 계약도 갱신한다.

## 검증 방법과 한계

- 각 커밋을 임시 디렉터리에 `git archive`로 추출했다. 원래 작업 트리의 브랜치·소스는 바꾸지 않았다.
- 두 스냅샷에서 기존 설치 의존성을 이용해 `npm run build` (`tsc --noEmit && vite build`)를 실행했고 모두 통과했다. Vite의 500KB 초과 청크 안내는 빌드 실패가 아니다.
- Node에서 대상 TypeScript를 실행해 실제 Sim·물리·이벤트 버스·기본 튜닝을 검사했다. 입력의 `consume()`에 넣는 눌림과 적 배치·HP·게이지·초기 조각 개방은 통제했다. 체크포인트·끝 지점은 좌표 배치 후 실제 프레임으로 판정했으며, 일부 방 적재·적 처치·재생성 검사는 해당 내부 메서드도 직접 호출했다.
- 카메라 검사는 실제 `LabScene.update()` 본문과 Sim에 모의 Phaser Scene·카메라를 연결한 호출 순서/대상 선택 검사다. UI 검사는 실제 `initUI()` 구독 코드와 모의 DOM의 클래스 상태를 사용했다. **이번 검토에서 실제 브라우저의 Phaser 카메라 행렬, CSS 화면·음성 출력은 실행 검증하지 않았다.** 시뮬레이션의 소리 범위 상태와 효과음 이벤트 구독은 확인했다.
- 출입구 연결 검사는 이동 트리거를 확인한 것이다. R1부터 R5까지 점프·대시만으로 완주하는 경로, 모든 튜닝 조합, 장시간 플레이의 손맛·성능은 검증하지 않았다.
